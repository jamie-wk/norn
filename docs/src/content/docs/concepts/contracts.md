---
title: Contracts & the client/worker split
description: Where Norn code runs, and how generated contracts give API code typed access to workflows without importing worker code.
---

A Norn application runs in three places, and each one may import different things. Contracts are what let the third place, your API, talk to workflows with full types while importing none of the worker's code.

## Three places code runs

```text
 ┌─────────────── worker process ───────────────┐     ┌──────── API / client ────────┐
 │ createWorker({ registry })                   │     │ createClient()               │
 │ activities, services, providers: full Node   │     │ .norn/contracts.ts           │
 │                                              │     │   (workflow types via        │
 │ ┌─────────── workflow sandbox ─────────────┐ │     │    import type only)         │
 │ │ .norn/workflows.ts, your @Workflow       │ │     │ Hono routes, scripts, jobs   │
 │ │ classes, .norn/activities.ts             │ │     └──────────────┬───────────────┘
 │ │ deterministic, no Node APIs              │ │                    │
 │ └──────────────────────────────────────────┘ │                    │ start, signal,
 └──────────────────────┬───────────────────────┘                    │ query, update
                        │ polls task queues                          │
                        ▼                                            ▼
                 ┌────────────────────── Temporal server ─────────────────────┐
                 └────────────────────────────────────────────────────────────┘
```

1. **The workflow sandbox.** Your `@Workflow` classes, and what they import, run in an isolated context inside the worker. They may import only workflow-safe code: see [Determinism & the sandbox](/norn/concepts/determinism/).
2. **The worker process.** Ordinary Node. It runs `createWorker()`, your `@Activities` classes and the services injected into them, and hosts the sandbox.
3. **The API and other clients.** Anything that starts workflows or sends them messages: a Hono app, a CLI script like the starter's `src/order.ts`, a cron job. It talks to the Temporal server, never to the worker directly.

The worker and the API never call each other. Both talk to the Temporal server, so the API only needs to know what to send: workflow type, task queue, workflow ID, handler names and the shapes of their arguments and results.

## What a contract is

`norn gen` writes one contract per workflow into `.norn/contracts.ts`:

```ts
// Generated by norn gen. Do not edit.

import { contract } from '@norn-ts/core';
import type { OrderWorkflow as OrderWorkflow$ } from '../src/workflows/order.workflow.js';

export const OrderWorkflow = contract<typeof OrderWorkflow$>()({
  name: 'OrderWorkflow',
  taskQueue: 'orders',
  id: 'order-{orderId}',
  signals: { cancel: 'cancel' },
  queries: { getStatus: 'getStatus' },
});
```

The workflow class comes in through `import type`, which TypeScript erases. At runtime a contract is a small object of names from `@norn-ts/core`. At compile time it carries everything the class declares: `run()`'s input and result, and every handler's arguments and result. The keys of `signals`, `queries` and `updates` are method names, which you use in code; the values are the names registered with Temporal.

API code imports the contract and hands it to the client:

```ts
import { createClient } from '@norn-ts/client';
import { OrderWorkflow } from '../.norn/contracts.js';

const norn = createClient();
const order = await norn.workflow(OrderWorkflow).start({ orderId: 'o-42', cents: 1999 });
```

## What is checked at compile time

Everything a call sends is checked against the workflow class. Here the contract is written inline, the way `norn gen` writes it, so the example is self-contained:

```ts twoslash
// @errors: 2345 2353
import { contract } from '@norn-ts/core';
import { createClient } from '@norn-ts/client';
import { Query, Signal, Workflow } from '@norn-ts/workflow';

@Workflow({ taskQueue: 'orders', id: 'order-{orderId}' })
export class OrderWorkflow {
  @Signal() cancel(_reason: string) {}
  @Query() getStatus(): 'pending' | 'paid' | 'refunded' {
    return 'pending';
  }
  async run(input: { orderId: string; cents: number }) {
    return 'paid' as const;
  }
}

const OrderContract = contract<typeof OrderWorkflow>()({
  name: 'OrderWorkflow',
  taskQueue: 'orders',
  id: 'order-{orderId}',
  signals: { cancel: 'cancel' },
  queries: { getStatus: 'getStatus' },
});

export async function example() {
  const orders = createClient().workflow(OrderContract);
  const order = orders.get({ orderId: 'o-42' });

  const status = await order.query('getStatus');
  //    ^?

  // a number is not a valid cancel reason
  await order.signal('cancel', 42);
  // the ID template needs orderId, not id
  orders.get({ id: 'o-42' });
}
```

In full, the compiler checks:

- **Workflow IDs.** Every `{placeholder}` in the `id` template must be a field of `run()`'s input; the `@Workflow` decorator itself fails to type-check otherwise. `get()` takes the template's fields, or an explicit `workflowId`.
- **Input and result.** `start()` and `execute()` take `run()`'s input type; `result()` returns its output.
- **Signals, queries and updates.** Names must be handler methods of that workflow. Arguments must match the method's parameters, and `query()` and `update()` return the method's result type.
- **Search attributes.** The names and types declared in `@Workflow({ searchAttributes })` type the `searchAttributes` start option and `describe()` results.

Some things are only known at runtime, and Norn checks those before the call reaches Temporal: ID placeholder values must be non-empty strings, numbers or bigints, and search attribute values must match their declared type. See [Client](/norn/guides/client/) for every method.

## Splitting worker and API into packages

In a single package, API code imports `.norn/contracts.ts` directly, as the starter's `src/order.ts` does. When the API deploys separately, have `norn gen` write a second copy of the contracts into a package of their own:

```ts
// worker/norn.config.ts
import { defineConfig } from '@norn-ts/cli';

export default defineConfig({
  include: ['src/**/*.ts'],
  contracts: { outFile: '../contracts/src/index.ts' },
});
```

```text
 worker/      workflows, activities, .norn/, createWorker()
 contracts/   src/index.ts written by norn gen; runtime dependency: @norn-ts/core
 api/         depends on contracts and @norn-ts/client, never on worker
```

The API's runtime code then contains `@norn-ts/core` and the contract objects, and nothing from the worker. The type checker still reads the workflow classes through the `import type`s, so a change to a workflow's signature breaks the API's build, not production. This is how `examples/orders` in the repository is laid out; [Project layout](/norn/guides/project-layout/#splitting-worker-and-api) has the details.

For a workflow implemented elsewhere (another service, another language), write the contract by hand with `defineWorkflow()`: see [Client: manual contracts](/norn/guides/client/#manual-contracts).
