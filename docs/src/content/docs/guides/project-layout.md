Norn projects have two kinds of code: the code you write (decorated classes) and the code `norn gen` writes for you in `.norn/`. This page explains why the generated files exist, what is in each one, and how to lay out a repository with separate worker and API deployments.

## Why generate code at all?

Three facts about Temporal shape everything Norn generates.

**1. The workflow sandbox cannot import activity code.** Workflows run in a deterministic V8 isolate and are bundled separately from the rest of the worker. If a workflow file imports your activity class, the bundle pulls in the activity module, its services, your database driver and probably `node:net`, and either fails to build or fails at runtime. Workflows need to know activity *names*, *options* and *types*, never their implementation. So `norn gen` writes `.norn/activities.ts`: one reference per activity class, holding the registered names and options as plain data, with the class imported **as a type only**.

**2. API code should never import worker code.** Your API needs to know that `OrderWorkflow` takes `{ orderId, cents }`, returns a status, and accepts a `cancel(reason: string)` signal. Importing the workflow class to learn that would drag workflow code, and everything it imports, into the API bundle. So `norn gen` writes `.norn/contracts.ts`: one contract per workflow, built with `contract<typeof OrderWorkflow>()`, where `OrderWorkflow` comes from an `import type`. The API gets full types, and its bundle contains a few small objects with names and task queues.

**3. Temporal registers workflows by export name.** A worker finds workflow functions by the export names of its workflows module, and that name is the workflow type that clients start. So `norn gen` writes `.norn/workflows.ts`, a barrel that exports each workflow under its type name, wrapped with `implement()`. It imports only workflow files, so it is a safe bundle entry point.

The rest follows from those: the worker needs to know the task queues, the bundle entry and how to build activities (`.norn/registry.ts` and `.norn/container.ts`), schedules and search attributes need to be created on the server (`schedules.json`, `search-attributes.json`), and renaming any registered name breaks running executions (`norn.lock.json`).

## How `norn gen` works

`norn gen` is a **syntax-only** analyzer built on [oxc-parser](https://oxc.rs). It parses the files matched by `include`, finds classes decorated with `@Workflow`, `@Activities` and `@Service`, and reads their options and constructor parameter types straight from the syntax tree. It never runs your code and never invokes the TypeScript compiler, which is why it takes milliseconds and works in `--watch` mode.

That design has a few rules:

- **Decorator options must be literals.** `@Workflow({ taskQueue: 'orders' })` is fine; `@Workflow({ taskQueue: QUEUE })`, spreads, function calls and template literals with expressions are reported as `non-literal`, with the location and a hint. The options end up in generated files, so they must be readable without running code.
- **Decorated classes must be named exports**, because generated files import them by name.
- **Constructor parameters of activity and service classes need type annotations** that resolve to a class, or to an interface with a same-named token (`export const Mailer = token<Mailer>('Mailer')`). Primitive, union, generic and rest parameters are not injectable; wrap such values in a token. See [Dependency injection](/norn/guides/dependency-injection/).
- **JSDoc comments on handler methods become descriptions** that the Temporal UI shows for signals, queries and updates.

Along the way it checks the things that would otherwise fail at bundle time, on replay, or in production: workflow files that import activity code, Node built-ins or worker-only packages (followed through relative imports transitively), non-deterministic globals in workflow code (`setTimeout`, `process`, `crypto.randomUUID`, `Temporal.Now`, ...), duplicate workflow, handler and activity names, `@Validate` methods that don't name an `@Update`, conflicting search attribute types across workflows, and renames of locked names. Errors are printed like compiler diagnostics:

```text
src/workflows/order.workflow.ts:4:1 - error norn(import-boundary): Workflow code must not import src/activities/payment.activities.ts, which declares @Activities or @Service classes
  hint: Use import type for types; workflows call activities through the generated activities file with useActivities().
```

## The generated files

Everything below lives in `outDir` (default `.norn/`). Commit it: reviewers see exactly what changed in the registered surface of your workers, and API code builds without running the generator. TypeScript files start with `// Generated by norn gen. Do not edit.`

### `workflows.ts`: the bundle entry point

```ts
// Generated by norn gen. Do not edit.

import { implement } from '@norn-ts/workflow';
import { OrderWorkflow as OrderWorkflow$ } from '../src/workflows/order.workflow.js';
import { CartWorkflow as ShoppingCart$ } from '../src/workflows/cart.workflow.js';

export const OrderWorkflow = implement(OrderWorkflow$, { descriptions: { cancel: 'Cancel the order and refund the charge.' } });
export const ShoppingCart = implement(ShoppingCart$);
```

Each export is named after the **workflow type** (`@Workflow({ name })`, defaulting to the class name), which is why `name` must be a valid identifier. `implement()` turns the class into the function Temporal runs: it constructs the class with the input, registers every handler, runs `run(input)` and waits for in-flight handlers. This file imports workflow files only.

### `activities.ts`: workflow-safe activity references

```ts
// Generated by norn gen. Do not edit.

import { defineActivities } from '@norn-ts/workflow';
import type { PaymentActivities as PaymentActivities$ } from '../src/activities/payment.activities.js';

export const PaymentActivities = defineActivities<PaymentActivities$>()({
  prefix: 'payments.',
  methods: {
    charge: { timeout: '30s', retries: 3, nonRetryable: ['CardDeclinedError'] },
    refund: { timeout: '30s', retries: 10 },
  },
});
```

Workflows import these references by the activity class's name and pass them to `useActivities()`. The class is imported with `import type`, so the reference carries the method signatures and nothing else. Errors listed in `@NonRetryable` are recorded by name so the workflow-side retry policy agrees with the worker.

### `contracts.ts`: typed contracts for clients

```ts
// Generated by norn gen. Do not edit.

import { contract } from '@norn-ts/core';
import type { OrderWorkflow as OrderWorkflow$ } from '../src/workflows/order.workflow.js';

export const OrderWorkflow = contract<typeof OrderWorkflow$>()({
  name: 'OrderWorkflow',
  taskQueue: 'orders',
  id: 'order-{orderId}',
  signals: { cancel: 'cancel' },
  queries: { getStatus: 'getStatus' },
});
```

Empty `signals`, `queries`, `updates` and `searchAttributes` maps are left out. A contract maps each handler's **method name** (the key you use in TypeScript) to its **registered name** (what goes over the wire). With `@Query('status') getStatus()`, the contract has `queries: { getStatus: 'status' }`, and you call `handle.query('getStatus')`. The input, output and argument types all come from the class through `typeof`, so changing a workflow's signature immediately breaks the API code that depends on it, at compile time.

You can also write contracts by hand with `defineWorkflow()`, for workflows implemented in another service or another language. See [Client](/norn/guides/client/#manual-contracts).

### `container.ts` and `registry.ts`: what the worker runs

`container.ts` imports your `@Activities` and `@Service` classes and your `providers` module, and exports `createNornContainer(options)`, which calls `createContainer()` with the dependency list of every class in constructor-parameter order. `registry.ts` exports a `registry` object that `createWorker()` and `createTestEnv()` take:

```ts
// Generated by norn gen. Do not edit. (abridged)
import { fileURLToPath } from 'node:url';
import type { NornRegistry } from '@norn-ts/worker';
import { createNornContainer } from './container.js';

// `.ts` when run from source (tests, tsx), `.js` once compiled.
const ext = import.meta.url.endsWith('.ts') ? '.ts' : '.js';

export const registry = {
  workflowsPath: fileURLToPath(new URL(`./workflows${ext}`, import.meta.url)),
  taskQueues: ['orders'],
  activities: ['payments.charge', 'payments.refund'],
  searchAttributes: {},
  createContainer: createNornContainer,
} satisfies NornRegistry;
```

These files import worker code, so only the worker (and tests) import them. See [the `@norn-ts/worker` reference](/norn/reference/worker/#the-registry) for every field.

### `schedules.json` and `search-attributes.json`

`schedules.json` lists every `@Schedule` (ID, workflow type, task queue, cron expressions, input and policies); `norn schedules sync` applies it to the server. `search-attributes.json` is the union of every workflow's `searchAttributes`, by name and type, for registering them on a namespace. See [Schedules](/norn/guides/schedules/) and [Client: search attributes](/norn/guides/client/#search-attributes).

### `norn.lock.json`: rename protection

The lock file sits next to `norn.config.ts` and records every registered name: workflow types with their task queues, signal, query and update names, and activity names.

```json
{
  "version": 1,
  "workflows": {
    "OrderWorkflow": { "taskQueue": "orders", "signals": ["cancel"], "queries": ["getStatus"], "updates": [] }
  },
  "activities": ["payments.charge", "payments.refund"]
}
```

Adding names is always fine. **Removing or renaming one, or moving a workflow to another task queue, fails `norn gen`**, because running executions still use the old name: a renamed signal is silently dropped, a renamed activity never gets picked up, and a workflow moved to a new task queue strands every execution on the old one. When the change is intentional (nothing is running, or you have migrated), run `norn gen --accept-rename`. See [Versioning & safe deploys](/norn/guides/versioning/).

## In CI and while developing

```sh
norn gen --check   # fails if any generated file is stale, without writing anything
norn gen --watch   # regenerates on every change
```

Run `--check` in CI next to `tsc` so a forgotten `norn gen` never ships. In development, run `--watch` in a terminal next to your worker, or put `norn gen` in front of your `build` and `test` scripts.

## Splitting worker and API

A single package is fine for small services. When the API and the worker deploy separately, put the contracts somewhere the API can import without depending on the worker package:

```ts
// worker/norn.config.ts
import { defineConfig } from '@norn-ts/cli';

export default defineConfig({
  include: ['src/**/*.ts'],
  providers: 'src/providers.ts',
  contracts: { outFile: '../contracts/src/index.ts' },
});
```

```text
packages/
├── worker/        # workflows, activities, services, .norn/, createWorker()
├── contracts/     # src/index.ts written by norn gen; depends on @norn-ts/core only
└── api/           # depends on @norn-ts/client and contracts; never on worker
```

`contracts/src/index.ts` is a second copy of `.norn/contracts.ts`. Because it uses `import type`, the contracts package needs the worker package only for type checking (a `devDependency`), and the API's runtime bundle contains `@norn-ts/core`'s small `contract()` helper and your contract objects. This is the layout of the `examples/orders` app in the repository.

## Files you write

Norn does not mandate a directory structure, but `norn gen` and the [ESLint plugin](/norn/guides/eslint/) recognise these conventions:

| Pattern | Meaning |
| --- | --- |
| `src/workflows/**`, `*.workflow.ts` | Workflow code: runs in the sandbox, linted for determinism. |
| `src/activities/**`, `*.activities.ts` | Activity classes: run in Node with full access. |
| `src/services/**`, `*.service.ts` | Services injected into activities. |
| `src/providers.ts` | `export const providers = [provide(...), ...]` for configuration and SDK clients. |
| `src/domain/**` or similar | Shared types and error classes. Keep these free of I/O so both sides can import them. |

Workflow files may import `@norn-ts/workflow`, `@norn-ts/core`, `@temporalio/workflow`, `@temporalio/common`, the generated `.norn/activities.ts`, other workflow files and pure modules. They must not import activity or service modules (except with `import type`), Node built-ins, or worker-side packages.
